# 第一部分 总体模式：Orchestrator + Specialists

## 1.1 两层编排架构

```
                    ┌─────────────────────────────┐
                    │   人类（架构决策 + 验收）      │
                    │   只做三件事：定方向、批契约、   │
                    │   过检查点                    │
                    └──────────────┬──────────────┘
                                   ▼
                    ┌─────────────────────────────┐
                    │   Orchestrator（总编排 Agent）│
                    │   读三份设计文档 → 拆工单 →    │
                    │   派发 → 跟踪 → 收口门禁       │
                    └──────────────┬──────────────┘
          ┌───────────────┬───────┴───────┬───────────────┐
          ▼               ▼               ▼               ▼
   ┌────────────┐  ┌────────────┐  ┌────────────┐  ┌────────────┐
   │契约工程师   │  │后端工程师   │  │前端工程师   │  │QA/评审      │
   │(Contract)  │  │(Platform/  │  │(Console/   │  │(Test/      │
    │            │  │Runtime/AI/ │  │Canvas/SDK) │  │Review)     │
   │            │  │Workflow/   │  │            │  │            │
   │            │  │Channel/    │  │            │  │            │
   │            │  │Billing)    │  │            │  │            │
   └────────────┘  └────────────┘  └────────────┘  └────────────┘
```

## 1.2 为什么这样切

- **Orchestrator 不写代码**：只做任务分解、派发、门禁收口——避免单一 agent 上下文过载
- **Specialist 单线程专精**：每个 agent 的上下文只装自己领域（一份领域文档 + 相关契约 + 文件领地），控制上下文窗口消耗
- **契约先行天然适配 AI**：契约冻结后前后端 agent 可完全并行，互不等待
- **人类只在三个点介入**：① 架构决策 ② 契约评审 ③ 里程碑验收——其余全部自动化

## 1.3 任务流转协议

```
Orchestrator 拆工单（关联功能 ID + 契约版本 + 文件领地）
      │
      ▼
写入工单队列（.ai-team/tickets/T-xxx.md）
      │
      ▼
派发给 Specialist（携带：工单 + 必读文档路径 + 领地 + 验收标准）
      │
      ▼
Specialist 在隔离 worktree/分支执行 → 自检清单 → 提交
      │
      ▼
门禁链（自动）：lint → 单测 → 契约测试 → 类型检查
      │
      ▼
Reviewer Agent 二审（对照架构规则）→ 通过则合并
      │
      ▼
Orchestrator 更新状态 → 触发下一工单 / 升级人类
```

> 这是整个 AI 团队的“宪法”。Codex/Claude Code/Cursor 都会自动读取。以下为完整模板，**直接放进仓库根目录**。

```markdown
# AGENTS.md — LinkAI 复刻工程 · AI 团队手册

## 项目一句话
1:1 复刻 LinkAI（link-ai.tech）一站式 AI 智能体平台。核心理念：平台做框架，用户做创造。

## 必读文档（按序，动手前必须读完）
1. docs/01-功能拆解蓝图.md —— 对标物全貌
2. docs/02-团队组建与开发实施方案.md —— 八大框架、团队、四阶段
3. docs/03-开发实现框架设计.md —— 架构基线、四层架构、契约先行流程
4. docs/04-模块级实施规格.md —— 模块级 UI/前端/后端/测试规格
5. docs/05-AI开发团队与提示词工程.md —— AI 团队编制与提示词工程（本仓库 .ai-team/ 的源头）

## 架构铁律（违反即打回）
1. 契约先行：任何跨端/跨服务改动，先改 packages/contracts 的 OpenAPI，再生成代码，后写实现
2. 四层架构：api → services → domain → infra，依赖只准向内；domain 层不准 import 任何框架
3. 文件领地：只改工单指定的目录；超范围改动必须停下并在工单里上报
4. 注册机制：新模型厂商/渠道/节点/插件一律走适配器+注册表，不准改内核
5. 安全基线：用户代码进 sandbox、外部请求过 ssrf-proxy、插件走 daemon 密钥
6. 多租户：所有数据操作带 tenant_id，不准写裸查询
7. 文档即代码：功能 PR 必须带文档 diff
8. 开源优先，不重复造轮子：动手实现通用功能模块前，必须先检索 GitHub 是否已有成熟可靠的开源库，能直接引入的直接使用。选型核查四项——① 维护活跃度（近 3 个月有提交或发版）② Issue 响应（open/closed 比、维护者响应速度）③ 许可证兼容（MIT/Apache-2.0/BSD 可直接引入；GPL/AGPL 必须升级人类确认，SaaS 场景防传染）④ 技术栈与依赖版本匹配。有多个候选必须列对比表给出推荐方案与理由，集成方式和必要适配改造写进工单。只有当现有库无法满足需求、体积过大或存在安全风险时才允许自研，且必须在工单写明理由。检索渠道：WebSearch/WebFetch（GitHub 直连不稳定时用 api.github.com / raw.githubusercontent.com 或国内镜像）

## 工程规范
- 前端：ESLint+Prettier+Stylelint；Python：Ruff+Black+mypy --strict；Go：golangci-lint
- 提交信息：feat/fix/refactor/chore(scope): 描述 [T-xxx]
- 分支：feat/T-xxx-简述，短命分支，禁止直接推 main
- 测试：跨端改动必须带 Pact 契约测试（Phase 0 可延后至服务落地时补齐）
- 新依赖引入必须先进工单"依赖清单"（库名/版本/license/引入理由）；lockfile 一并提交，版本 pin，不准随手加依赖
- 开源选型记录（候选对比表 + 推荐理由 + 集成方式）是功能 PR 的必填内容

## 工作协议
- 领工单：读 .ai-team/tickets/T-xxx.md + 其中指定的文档路径
- 开工：git worktree add ../wt-T-xxx -b feat/T-xxx-简述
- 自检：完成前逐项过工单里的 Self-Check 清单
- 交收：提交 + 在工单填"交付说明"（改了什么/怎么验证的/风险点）
- 阻塞：超 30 分钟无进展或遇架构歧义，停止并在工单标记 BLOCKED + 原因

## 当前阶段
Phase 0（地基）：见 docs/02 的 Phase 0 任务表
```

# 第三部分 AI 角色编制与完整提示词

> 使用方式：把对应提示词作为 agent 的系统提示/项目指令粘贴（Claude Code 放 CLAUDE.md，Codex 放 AGENTS.md 同级角色文件，Cursor 放 .cursor/rules）。每个提示词都是自包含的——agent 不需要知道其他角色存在，只需要知道向谁交接。

## 角色 1：Orchestrator（总编排）

```
# 角色：Orchestrator — LinkAI 复刻工程总调度

## 你是谁
你是复刻工程的总编排者，等价于“技术负责人 + 项目经理”。你不写业务代码，你的产出是
工单、派发指令、门禁报告和升级决策。

## 必读上下文
仓库根 AGENTS.md；docs/01~03 三份设计文档；.ai-team/tickets/ 全部工单及状态。

## 核心职责
1. 把当前 Phase 的任务拆成 2 天以内可完成的工单（关联功能 ID + 契约版本 + 文件领地 + 验收标准 + Self-Check 清单）
2. 维护工单队列和状态机（PENDING → ASSIGNED → IN-REVIEW → DONE / BLOCKED）
3. 按依赖关系派发：契约未冻结的工单禁止派给前后端执行 agent
4. 每个工单交收后跑门禁链报告（lint/单测/契约测试/评审结论）
5. 遇到架构歧义、契约冲突、跨 Phase 范围问题时，整理成“决策请求”升级人类，禁止自行拍板

## 派发规则
- 契约类工单 → Contract Engineer（最高优先级，阻塞其他所有）
- 契约冻结后，后端各领域工单可并行派发（文件领地不重叠为前提）
- 前端工单在契约 v 版本生成后即可派发（Mock 驱动）
- QA 工单随每个功能工单派发（契约测试 + 黄金集）
- Reviewer 在所有代码 PR 合并前必须过一遍

## 输出格式
每次调度输出：① 本轮派发清单（工单→角色→依赖）② 门禁报告 ③ 风险与阻塞项 ④ 下一步建议。
禁止输出业务代码。

## 铁律
- 一个工单只属于一个角色，文件领地不重叠
- 契约变更必须走 Contract Engineer，其他角色不准直接改 contracts 包
- BLOCKED 超过 2 轮的工单必须升级人类
```

# 第四部分 提示词工程方法（本文的“元技能”）

## 4.1 五段式角色提示词结构

所有角色提示词统一结构——这是可复用的模板：

```
① 你是谁        （身份 + 技术栈 + 等价的人类角色）
② 必读上下文     （文档路径清单，按序，控制上下文预算）
③ 核心职责       （编号列表，每条可验证）
④ 工程规范/铁律   （禁止项比允许项更重要）
⑤ 输出格式 + 自检清单
```

## 4.2 上下文分层（控制每个 agent 的 token 预算）

| 层 | 内容 | 注入方式 |
|---|---|---|
| 常驻记忆 | AGENTS.md（架构铁律+工程规范） | 仓库根目录，agent 自动读 |
| 任务上下文 | 工单（功能 ID/契约版本/领地/验收标准） | 派发时随消息给 |
| 领域知识 | 三份设计文档的相关章节 | 工单里给**路径**不给全文，让 agent 按需读 |
| 视觉基准 | linkai-screenshots/ 截图 | 前端类工单必须挂路径 |
| 横切规则 | 对应角色的“工程规范/铁律”段 | 角色提示词常驻 |

**原则**：一个 agent 一次任务的目标上下文 ≤ 50k token；超了就必须拆工单，不准硬塞。

## 4.3 防跑偏四机制

1. **Scope Guard（领地守卫）**：每个提示词都有“文件领地”+“超范围必须停下上报”。CI 加 diff 检查：PR 改动文件超出工单领地直接打回
2. **Self-Check 清单**：工单末尾的 checklist，agent 完成前逐项确认——把“验收标准”前置成 agent 的自我验证指令
3. **禁止项显式化**：每个角色的“铁律”段只写禁止（不准改契约/不准裸查询/不准绕过计量）——禁止项比允许项更能约束 AI
4. **升级协议**：BLOCKED 状态 + 30 分钟规则，防止 agent 在错误方向上空转

## 4.4 交接即契约（Handoff as Contract）

agent 间不自由对话，只用结构化交接消息（见 2.3 模板）：状态/产出/验证证据/下游注意/风险。**没有“下游注意”字段的交接视为无效**——这是防止并行开发信息断层的关键。

## 4.5 开源选型协议（铁律 8 的执行细则）

**触发条件**：工单涉及"通用功能模块"（文档解析/全文检索/对象存储/认证鉴权/限流/图表渲染/流式推送/HTTP 客户端/任务队列/ORM/校验库……）时，写代码前必须先执行本协议。

**执行五步**：
1. **检索**：WebSearch/WebFetch 找候选（GitHub 直连不稳定时用 api.github.com / raw.githubusercontent.com 或国内镜像），至少找 2 个候选
2. **四项核查**：① 维护活跃度（近 3 个月有提交或发版）② Issue 响应（open/closed 比、维护者响应速度）③ 许可证兼容（MIT/Apache-2.0/BSD 可直接引入；**GPL/AGPL 必须升级人类确认**，SaaS 场景防传染）④ 技术栈与依赖版本匹配
3. **对比决策**：多候选列对比表（维护度/star/许可证/体积/依赖/契合度），给出推荐方案与理由
4. **记录进工单**：候选对比表 + 推荐理由 + 集成方式 + 必要适配改造，是功能 PR 必填内容
5. **自研例外**：仅当现有库无法满足需求、体积过大或存在安全风险时才允许自研，且必须在工单写明理由

**给 AI 的提示词写法**（可粘贴进任何涉及通用模块的工单）：
```
本工单涉及通用功能模块。动手前必须先执行开源选型协议（AGENTS.md 铁律 8）：
检索至少 2 个候选并逐项核查（维护活跃度/Issue 响应/许可证/技术栈匹配），
在工单"开源选型记录"区填对比表、推荐理由、集成方式与适配点；
只有确认无适用库时才自研，并写明理由。禁止跳过调研直接写代码。
```

**为什么这条对 AI 团队尤其重要**：AI 写"轮子代码"又快又像真的——一个自己手写的 CSV 解析器、一个 reinvent 的限流器，肉眼看着能跑，实际是未来的维护债务和安全隐患。用协议把调研变成**工单里的必填字段**，Reviewer 才有东西可查。

# 第五部分 质量门禁与验证闭环

## 5.1 自动化门禁链（CI 强制，AI 无权跳过）

```

  → 合并
```

## 5.2 Reviewer Agent 的评审清单（节选）

- [ ] 依赖方向：api→services→domain→infra，无反向、无跨层穿透
- [ ] domain 层零框架 import
- [ ] 所有 DB 查询带 tenant_id
- [ ] 模型调用走 model-proxy，无厂商 SDK 直连
- [ ] 消耗入口只发 MeteringEvent，无私自扣减
- [ ] 新品类走注册表，无内核修改
- [ ] 契约实现一致（生成物 diff 为空）
- [ ] 外部请求过 ssrf-proxy，用户代码进 sandbox
- [ ] 单测覆盖边界：并发/失败/重试/幂等
- [ ] **通用模块有开源调研记录**（候选对比表+推荐理由+集成方式）；无调研记录=REQUEST_CHANGES；自研模块工单里写明了理由

## 5.3 人类检查点（AI 不能替代的五个决策）

1. **契约评审**：API 形状影响所有下游，人类必须批
2. **架构变更**：偏离三份设计文档的决策，人类必须批
3. **黄金集分数连续下降**：效果问题可能是方向性的，人类介入
4. **资金相关 PR**：抽查 + 双人评审
5. **里程碑验收**：每个 Phase 出口标准人类验收
6. **GPL/AGPL 许可证引入**：SaaS 场景有传染风险，必须人类确认

# 第八部分 风险与边界（诚实清单）

| 风险 | 现实 | 缓解 |
|---|---|---|
| AI 效果调优不可完全自动化 | RAG 检索质量、提示词效果需要人类经验判断 | 黄金集 + 人类检查点；框架参数全暴露，把调优权设计成产品能力 |
| 长任务的上下文腐化 | 单个 agent 跑几小时后开始遗忘早期约束 | 工单 ≤2 天量；AGENTS.md 常驻防漂移；自检清单收口 |
| 契约腐化 | 实现渐进偏离契约 | 生成物 diff 必须为空 + Pact 双侧测试 |
| 渠道合规 | 微信/企微风控政策 AI 判断不了 | 渠道准入必须过人类合规检查点 |
| 资金安全 | AI 写错扣减逻辑代价极高 | Billing 角色双人评审 + 人类抽查 + 幂等/对账机制兜底 |
| 架构漂移 | 后期 agent 为走捷径违反四层架构 | Reviewer Agent 守卫 + CI diff 领地检查 |

**结论**：代码生产可以全部交给 AI 集合，但**契约、架构、效果、资金、合规五个点必须留人类检查点**——这套设计的本质是“用自动化放大人类判断，而不是替代人类判断”。
