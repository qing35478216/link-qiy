# LinkAI 复刻 · 开发实现框架设计（参考 Dify 优化版）

> 定位：在《LinkAI复刻-团队组建与开发实施方案.md》（框架优先版）之上，深入一层——**前后端分离的工程实现框架**。
> 参考对象：Dify（langgenius/dify，Apache 2.0 + 附加条款）——目前开源 LLM 应用平台中架构最完整的工程样本。
> 方法：拆解 Dify 的七大设计 → 保留其精髓 → 针对其痛点做四项优化 → 落地为我们的 monorepo、契约先行流程、服务划分和文档体系。

# 第一部分 Dify 架构解析：借什么，改什么

## 1.1 Dify 工程形态全貌（2026 现状）

```
dify/（monorepo）
├── api/            # Python Flask 后端（RESTX + Pydantic 配置 + Gunicorn/gevent）
│   ├── controllers/  # HTTP 接口层
│   ├── services/     # 业务编排层
│   ├── core/         # 编排引擎/Agent 执行器/RAG 链路/插件实现
│   ├── models/       # SQLAlchemy 数据模型
│   └── configs/      # Pydantic 分层配置（feature/__init__.py）
├── web/            # Next.js + React 控制台（zustand/jotai + React Flow 画布）
├── sandbox/        # Go 编写的代码执行沙箱（独立服务）
├── docker/         # docker-compose 编排
└── 部署形态：单镜像 dify-api 靠 MODE 环境变量切换 api/worker/beat 角色
```

**运行时组件**：api（Flask，REST 双 API——console API + service API，CORS 分离）｜worker（Celery，队列按 dataset/workflow/mail/trigger/plugin 分离）｜web（Next.js）｜PostgreSQL 15｜Redis（缓存+Celery broker）｜向量库（23+ provider 工厂抽象）｜plugin_daemon（插件守护进程，独立服务+共享密钥）｜ssrf_proxy（SSRF 防护代理）｜sandbox（Go 沙箱）｜OpenDAL（存储抽象）。

## 1.2 Dify 七大值得继承的设计

| # | 设计 | 精髓 | 我们的继承方式 |
|---|---|---|---|
| 1 | **单镜像多角色**（MODE 切换 api/worker/beat） | 部署单元极简，CI 只构建一个镜像 | 沿用：每个服务一个镜像多角色，本地/云部署形态一致 |
| 2 | **图引擎与产品上下文分离**（Graphon 引擎 + node factory/layers 注入租户/配额/持久化） | 引擎可独立演进，不耦合业务 | **重点继承**：工作流引擎做成纯执行内核，产品关注点（租户/计费/审计）通过节点工厂注入 |
| 3 | **plugin daemon 独立服务** | 模型/工具是最高易变区，隔离成独立进程+密钥 | 继承并强化：gRPC 通信、插件市场元数据独立部署 |
| 4 | **向量后端工厂抽象**（registry + provider 包 + 依赖分组） | 支持 23+ 向量库而不让核心包膨胀 | 继承：provider 分包 + 依赖可选安装 |
| 5 | **Celery 队列按业务分离** | 文档解析慢任务不阻塞对话链路 | 继承：队列按框架分（knowledge/workflow/plugin/billing/trigger） |
| 6 | **前端深度理解运行时事件**（SSE 事件流 → 画布实时状态：执行中/节点结果/人工输入/追踪） | 画布不是 CRUD，是运行时事件的投影 | **重点继承**：建立统一 Runtime Event 协议，画布/调试窗/对话页共享 |
| 7 | **安全边界显式化**（SSRF proxy/sandbox/daemon 密钥/CORS 三角分离/OTel trace 头穿透） | LLM 平台接受外部输入/URL/文件/插件，边界比功能更重要 | 继承：全部纳入架构基线，安全评审进 Definition of Done |

## 1.3 Dify 的五个痛点与我们的优化

| # | Dify 痛点 | 我们的优化 |
|---|---|---|
| 1 | **单体 api/ 过度膨胀**：core/ 包太大，小改动牵动 API+worker+daemon+前端+migration | 按八大框架拆**独立服务**（见第二部分），服务内四层架构，跨服务只走契约 |
| 2 | **Flask 同步模型**：高并发对话/流式场景 worker 吃紧 | 热路径（网关/渠道/流式对话）用 **FastAPI 异步 + Go 网关**；Python 专注 AI 逻辑 |
| 3 | **契约弱耦合**：RESTX 注解驱动，前端类型靠手抄 | **契约先行**：OpenAPI 3.1 单一事实源 → 自动生成前后端代码 + Mock（第五部分） |
| 4 | **计费/商业化是短板**：社区版无完善计量计费 | 变现框架**内建于服务层**：统一计量服务 + 积分原子扣减，不是后期补丁 |
| 5 | **部署选项爆炸**：compose 里向量库/DB 可选项太多，生产难收敛 | Helm Chart + 环境分层（dev/staging/prod）+ 默认组合收敛（PG+pgvector+Redis+MinIO） |

## 2.3 前后端分离的三个决策

1. **BFF 不入驻前端**：控制台直连 gateway 的 console API；面向 C 端的 service API（开放 API/嵌入 SDK/渠道消息）走同一 gateway 的独立路由组 + CORS 分离（继承 Dify 的三角分离）
2. **前端多形态不强迫统一**：控制台 Vue3（忠实复刻 LinkAI 交互）、营销站 Next.js（SEO）、Studio React（画布生态）——**契约统一在 packages/contracts，技术栈按场景选**
3. **实时通信双通道**：控制台调试/画布用 SSE（Runtime Event 流）；渠道消息走 gateway 的 WebSocket/长连接（Go 的优势场景）

# 第三部分 后端深度设计

## 3.1 服务内四层架构（所有 Python 服务统一）

```
services/<name>/src/
├── api/            # ① 接口层：FastAPI Router，参数校验，鉴权，序列化
│   └── 只做协议转换，不含业务
├── services/       # ② 应用层：业务编排，事务边界，领域事件发布
├── domain/         # ③ 领域层：实体/值对象/仓储接口/领域服务（纯 Python，无框架依赖）
│   └── 可单测，不碰 DB
└── infra/          # ④ 基础设施层：SQLAlchemy 实现/Redis/MQ/外部客户端/厂商适配器
```

**规则**：依赖只准向内（api→services→domain）；infra 实现 domain 定义的接口；跨服务禁止直接查库，只走契约 API 或事件。

## 3.2 技术栈选型（对标 Dify 的优化）

| 组件 | Dify | 我们 | 优化理由 |
|---|---|---|---|
| Web 框架 | Flask + RESTX | **FastAPI** | 原生异步（流式对话）、Pydantic 校验、**OpenAPI 自动生成**（契约先生的地基） |
| 网关 | Flask 内置 | **Go（自研轻量）** | 前后端分离的统一入口；渠道 WebSocket 长连接；限流/熔断 |
| 异步任务 | Celery + Redis | Celery + Redis（队列按业务分） | 成熟稳定，沿用；队列：knowledge/workflow/plugin/billing/trigger/mail |
| 工作流引擎 | Graphon（图内核+上下文注入） | **自研同构**：纯执行内核 + 节点工厂注入租户/配额/审计 | 引擎与产品上下文分离是精髓，必须继承 |
| 插件运行时 | plugin daemon（Python） | plugin daemon + **gRPC** | 类型安全契约；插件可用 Python/Go/Node 编写 |
| 代码沙箱 | Go sandbox | 同左 | 安全边界不变 |
| SSRF | ssrf_proxy | 同左 | 安全边界不变 |
| 向量库 | 23 provider 工厂 | 工厂抽象，**默认 pgvector** | 部署收敛；provider 分包可选依赖 |
| 存储 | OpenDAL | OpenDAL / 自研薄封装 | 多后端（本地/S3/OSS/COS） |
| 主库 | PostgreSQL 15 | PostgreSQL 16 + pgvector | 减少一个部署组件 |
| 可观测 | OTel + Langfuse 等 | OTel + 自建 trace + Prometheus | trace 头全链路穿透（继承） |

## 3.3 领域划分（八大框架 → 服务映射）

| 框架 | 服务 | 核心领域对象 | 关键机制 |
|---|---|---|---|
| 模型 | model-proxy | ModelProvider/Adapter/ModelCard/Invocation | 厂商适配器注册、降级链、token 计量埋点 |
| 提示词 | platform（app 域） | PromptTemplate/PromptVersion | 变量占位、一键优化服务、版本灰度 |
| 知识 | knowledge | Dataset/Document/Segment/RetrievalPolicy | 导入管道（解析器注册）、混合检索、查询改写 |
| 工具 | plugin-daemon | Plugin/Tool/McpServer | 意图路由、执行链记录、沙箱执行 |
| 流程 | workflow | Graph/Node/Edge/Variable/Execution | 图内核、节点工厂、执行快照、断点调试 |
| 接入 | gateway | Channel/Message/DeliveryRecord | 渠道适配器、统一消息模型、流式输出 |
| 分发 | platform（plaza 域） | Template/PublishedApp/Category | 一键复制、排行算法、审核管道 |
| 变现 | billing | Quota/PointAccount/Order/Settlement | 配额校验、原子扣减、对账校准 |

## 3.4 四个横切机制（后端核心）

**① 多租户穿透**：tenant_id 从网关注入上下文，全链路透传；ORM 行级过滤 + Redis key 前缀 + 向量库 partition 三级隔离。

**② 统一计量**：所有消耗入口（模型调用/插件/导入/执行）发 `MeteringEvent` 到 MQ → billing 原子扣减积分。入口只发事件，不感知计费规则。

**③ 领域事件总线**：服务内同步事件 + 跨服务 MQ 异步事件（AppPublished → plaza 索引；IndexingCompleted → 通知；UsageRecorded → 看板/收益）。

**④ 运行时事件协议（Runtime Event）**：前后端共享的统一事件 schema（借鉴 Dify 画布对 runtime events 的深度理解）：

```json
{ "event": "node_started | node_finished | message_chunk | tool_called | thought | error | human_input_required",
  "trace_id": "...", "node_id": "...", "payload": {...} }
```

画布调试、对话页、渠道流式输出、API 流式响应——全部消费同一事件流，只是渲染方式不同。

## 3.5 工作流引擎设计（Dify Graphon 模式复刻）

```
┌────────────────────────────────────────────┐
│  产品上下文层（Dify 的 layers/node factory） │
│  租户 · 配额校验 · 审计 · 持久化 · 通知      │
├────────────────────────────────────────────┤
│  图执行内核（纯函数式，无业务依赖）           │
│  DAG 校验 → 拓扑执行 → 变量池 → 分支/循环    │
│  节点 = 注册表里的实现，输入输出走 Variable   │
├────────────────────────────────────────────┤
│  节点实现层（注册即可扩展）                   │
│  llm / knowledge / plugin / code / branch / │
│  scheduler / channel-send / manual / ...    │
└────────────────────────────────────────────┘
```

- 节点注册表前后端共用（packages/node-registry）：加节点 = 注册表加一条 + 内核加一个类，画布自动出现
- 执行快照：每个节点的输入/输出/耗时落库，支持单节点重跑（复刻 LinkAI 的单节点调试）
- 代码节点进 Go sandbox；HTTP/插件节点过 ssrf_proxy

## 4.1 技术栈与形态

| 应用 | 栈 | 关键库 |
|---|---|---|
| 控制台 | Vue3 + TS + Vite | Element Plus（复刻 LinkAI 视觉）、Pinia、Vue Router、TanStack Query |

```
│   ├── app/              #   应用工厂/配置七件套/调试
│   ├── knowledge/        #   知识库/导入向导/检索测试
│   ├── workflow/         #   编排画布/节点面板/运行调试
│   ├── plugin/           #   插件中心/自定义插件
│   ├── channel/          #   渠道接入/客户端管理
│   ├── billing/          #   账户/积分/订单/使用记录
│   └── dashboard/        #   数据看板
├── shared/               # 跨模块共享：组件/hooks/工具/常量
├── api/                  # ★ 契约自动生成的客户端（sdk-ts）

```

**规则**：features 之间禁止互相 import（跨模块需求下沉 shared）；api/types 一律生成，禁止手写。

## 4.3 画布前端架构（全站最复杂，重点设计）

```
┌──────────────┐   ┌──────────────┐   ┌─────────────────┐
│ 节点注册表    │──▶│ 画布 Store   │◀──│ 命令面板/属性面板 │
│ (共享包)     │   │ (图结构+变量) │   │ (按节点类型渲染)  │
└──────────────┘   └──────┬───────┘   └─────────────────┘
                          │
              ┌───────────┴────────────┐
              ▼                        ▼
      ┌──────────────┐        ┌───────────────┐
      │ SSE 事件流    │        │ 本地调试态     │
      │ (运行时投影)  │        │ (草稿/校验)    │
      └──────────────┘        └───────────────┘
```

- **节点注册表驱动**：前端节点定义（端口/字段/默认值）与后端节点注册表同源（packages/node-registry），新增节点类型画布零改动
- **运行时投影**：SSE 事件流直接驱动画布节点状态（等待/执行中/成功/失败/输出预览），复刻 LinkAI 的"执行过程+思考过程"可视化
- **草稿与运行态分离**：编辑改本地草稿，保存才落库；运行看运行时快照，避免调试污染画布

# 第五部分 前后端分离协作流程（契约先行）

## 5.1 单一事实源：packages/contracts

```
packages/contracts/
├── openapi/
│   ├── console-api.yaml      # 控制台 API（管理面）
│   ├── service-api.yaml      # 开放 API（用户面，OpenAI 兼容）
│   └── runtime-events.yaml   # SSE 事件协议
├── schemas/                  # 复用模型（分文件，$ref 引用）
├── spectral.yaml             # 契约 lint 规则
└── 生成脚本 → sdk-ts / sdk-py / FastAPI 桩 / Mock Server
```

**流程（Contract-First Development）**：

```
① 定契约：PM+前后端+架构师评审 OpenAPI 变更（PR 进 contracts 包）
        ↓
② 机检：CI 跑 spectral lint + oasdiff  breaking change 检测（不兼容改动必须升版本）
        ↓
③ 代码生成（CI 自动）：
   · 前端：sdk-ts（类型安全客户端）+ TanStack Query hooks + MSW Mock handlers
   · 后端：Pydantic 模型 + FastAPI 路由桩（实现体留空待填）
        ↓
④ 并行开发（双轨，互不阻塞）：
   前端：MSW Mock 驱动 UI → 组件测试 → 契约测试（Pact）
   后端：填实现 → 领域单测 → 契约测试（Pact）→ 提交
        ↓
⑤ 联调 = 契约测试双方通过（Pact broker 比对），无需人工对接口
        ↓
⑥ 预览环境：PR 自动部署前后端 → QA/E2E（Playwright 跑关键用户旅程）
```

## 5.2 环境策略

| 环境 | 用途 | 数据 |
|---|---|---|
| local | `docker-compose up` 起依赖（PG/Redis/MinIO/向量库/ssrf-proxy）+ 各服务本地跑 | 种子数据 |
| preview | 每个 PR 一套 namespace（K8s）+ 前端预览部署 | 脱敏快照 |
| staging |  nightly 部署，全量回归 + 效果评测集 | 脱敏全量 |
| production | Helm 滚动发布，按服务独立发布 | 真量 |

**联调原则**：契约测试通过即视为可联调；环境只用于验证"真实依赖行为"（模型延迟、渠道回调）。

## 5.3 分支与发布

- trunk-based development，短命分支（≤2 天），feature flag 控制未完成功能
- 微服务独立 CI/CD（改动哪个服务发布哪个）；前端独立发布；契约包变更触发前后端双方 CI
- 语义化版本 + Changesets；数据库 migration 向前兼容（扩展-迁移-收缩三步法）

# 第七部分 文档体系（文档即代码）

## 7.1 文档分层（六类，全部进 monorepo 的 docs/）

| 层 | 内容 | 生产者 | 更新时机 |
|---|---|---|---|
| ① ADR | 架构决策记录（为什么 FastAPI 不用 Flask、为什么自研图引擎…） | 架构师 | 每个重大决策，不可改只可追加新 ADR  supersede |
| ② 契约文档 | OpenAPI 自动生成的参考文档 + 人工写的使用指南 | 契约+生成 | 契约变更自动重建 |
| ③ 领域文档 | 八大框架各一份：领域模型/关键流程/扩展点/坑 | 各框架负责人 | 设计变更随 PR |
| ④ 开发指南 | 新人 1 小时上手：环境/规范/契约流程/测试要求 | 前端组长+后端组长 | 每迭代 |
| ⑤ 运行手册 | 部署/监控/告警/故障处理/值班 | DevOps | 每次架构变更 |
| ⑥ 产品文档 | 对外帮助中心（docs 站，VitePress） | PM | 功能上线 |

## 7.2 文档管理机制

- **文档与代码同仓库**：`docs/` 目录，Markdown + MDX，VitePress 构建发布
- **CI 门禁**：链接有效性检查（lychee）；ADR 编号连续性；契约变更必须同步 ②③；新功能 PR 必须带文档 diff（CODEOWNERS 指定各目录 review 人）
- **单一事实源原则**：能自动生成的不手写（API 参考/类型/SDK 用法）；手写只写"为什么"和"怎么做"
- **llms.txt**：文档站输出 llms.txt/llms-full.txt（继承 LinkAI 的做法，让 AI 工具直接读文档）

# 附录：与 Dify 的关键差异速查

| 维度 | Dify | 我们 |
|---|---|---|
| 后端形态 | 单体 Flask（api/ 包揽） | 按八大框架拆服务，服务内四层 |
| Web 框架 | Flask + RESTX | FastAPI（异步+自动 OpenAPI） |
| 网关 | 内置 | Go 独立网关（含渠道长连接） |
| 前端 | 全站 Next.js | 按场景分工：Vue3 控制台/Next.js 营销站/React 画布 |
| 契约 | 注解驱动，弱契约 | OpenAPI 单一事实源 + 代码生成 + Pact |
| 图引擎 | Graphon（内核+注入） | 同构自研（内核+节点工厂注入） |
| 插件 | daemon（Python） | daemon + gRPC（多语言插件） |
| 计费 | 社区版弱 | 内建统一计量+积分原子服务 |
| 部署 | compose 可选项爆炸 | Helm + 默认组合收敛 |
| 文档 | README+社区 | 六层文档体系 + CI 门禁 + llms.txt |
