## P-001 ⚠️ 资损：Decimal 量化精度过粗，导致极低单价模型调用变成"免费"

**分类**：资损 / 数值精度 · **发现于** T-005 · **状态**：已修复

### 现象

积分折算器对 `input_per_1k = 0.0001`（即每千 token 0.0001 积分）的模型，
计算 1000+1000 token 的消耗时返回 **0 积分**——本应至少 1 积分。
等于该模型对平台**完全免费**。

### 根因

折算流程是：`raw = tokens/1000 × price` → `quantize(1e-6)` → `ceiling`。

`0.0001 × 1 = 0.0001`，而 `0.0001` 量化到 `1e-6` 精度后变成 `0.000000`——
**量化步骤把有效数字直接截没了**，随后的 `ceiling(0) = 0`。
设计时的意图是"量化只为吸收浮点噪声"，但精度选得比计费粒度还粗时，
它就从"去噪"变成了"抹除"。

**为什么测试没提前发现**：初始用例只覆盖了 `input_per_1k=1.0` 这类整数值，
浮点误差不可见。低价模型才暴露。

### 修复

噪声精度从 `1e-6` 收紧到 `1e-9`，并加固化用例：

```python
# 1/1000 × 0.0001 = 1e-7 → ceiling 1（极低单价也不得为 0）
assert calculator.compute(ModelPrice(0.0001, 0), TokenUsage.of(1, 1)) == 1
```

### 如何防止重演

**通用规则：量化/舍入的精度必须显著细于业务最小计费粒度。**

新增任何"数值 → 整数金额/积分"的转换时，必须回答：
1. 业务上**最小的一次计费**是多大？（单价 × 最小 token 数）
2. 我的量化精度比它**小几个数量级**？至少 2~3 个数量级。
3. 是否有用例**专门验证最小计费场景**？没有就补上。

**T-007 特别提示**：积分钱包涉及真实资金，必然也会做金额换算与对账。
建议直接复用 `services/model-proxy/src/linkai_model_proxy/domain/metering.py`
的 `CreditCalculator`（已按上述规则实现并被契约测试冻结），
不要另写一套舍入逻辑。

## P-002 资损风险：流式响应的终局事件早于计费计算 yield，客户端收到 credits=0

**分类**：资损 / 异步流时序 · **发现于** T-005 · **状态**：已修复

### 现象

SSE 流式对话中，协议规定的终局事件 `done` 携带 `usage.credits`（本次消耗积分）。
但客户端**恒定收到 `credits: 0`**，而实际调用的积分已正确记入计量事件。

### 根因

典型的"先yield 后计算"时序错误。原实现：

```
async for delta in adapter.stream(...):
    yield delta              # ← 终局分片在此刻已yield 出去
usage = calculate_credits()  # ← 积分在这里才算出来，已经晚了
```

生成器（async generator）一旦 `yield`，消费方立刻拿到该值；
后续计算再正确也无法回溯修改已发出的数据。

**为什么容易犯**：非流式路径没有这个问题——`return` 前算好再返回，
天然顺序正确。只有流式才会暴露。**同一个逻辑写两遍，流式那份几乎必然漏。**

### 修复

**扣住终局分片，等计费算完再 yield**：

```python
terminal = None
async for delta in adapter.stream(...):
    if delta.is_terminal:
        terminal = delta      # 扣住，不 yield
        continue
    yield delta
usage = self._credits.with_credits(card.price, usage)   # 先算
yield StreamDelta(..., usage=usage)                      # 再发
```

附带收益：若厂商没有给终局分片，现在会补一个 `stop` 的终局，
保证消费端总能收到 `done`，**不必依赖连接关闭**（runtime-events 协议的明确要求）。

### 如何防止重演

- 凡"**先产出、后加工**"的流水线，加工结果要么进产出物之前的环节，
  要么对已产出物**不可变**（否则就是本条 bug）。
- 写非流式与流式两份逻辑时，**共用同一个"结算"函数**，不要各写一遍。
- 契约里带金额/用量的字段，务必有一条断言：**该字段值 > 0**，
  或与计量事件的值相等。只断言"字段存在"是抓不到这类 bug 的。

## P-003 语义混淆：一个布尔量承担两种含义，导致 HTTP 状态码错报

**分类**：架构 / 语义设计 · **发现于** T-005 · **状态**：已修复

### 现象

降级链所有候选都失败时（`ModelCallFailure`），接口返回 **400 Bad Request**。
但这明明是"上游厂商全挂了"，应是 **502 Bad Gateway**。
客户端据此判断为"我的请求写错了"，不会重试——而实际上重试可能就成功了。

### 根因

异常上有一个 `retriable` 布尔量，本意是"降级链是否该切下一个候选模型"；
但代码里同时用它推导了 HTTP 状态码：

```python
return JSONResponse(status_code=502 if exc.retriable else 400, ...)
```

于是产生了一个**语义上自相矛盾的状态**：
`ModelCallFailure` 被显式设为 `retriable=False`（不再降级，因为候选已耗尽），
却被推导成"这是客户端的错误"。

**两个维度被强行压成了一个**：*内部是否继续处理* 与 *对外该报什么错*，它们是正交的。

### 修复

拆成三个正交字段：

| 字段 | 语义 | 谁读|
|---|---|---|
| `code` | 稳定机器码（`MODEL_CALL_FAILED`） | 客户端分支 |
| `retriable` | 降级链内部判断：是否切下一候选 | 编排层 |
| `client_status` | 对外 HTTP 状态码 | api 层 |

`ModelCallFailure(retriable=False, client_status=502)`——两个维度各司其职，不再打架。

### 如何防止重演

- **一个字段只承载一个维度。** 发现"某布尔量在不同地方影响不同决策"时，
  优先怀疑它承担了多重语义。
- 状态码**不要从业务标志推导**，应由异常类型自己声明（`client_status`）。
- 这类问题不会报错、只会"行为不符合预期"，靠 review 很难发现——
  写用例时**按每个错误码枚举预期状态码**，比只测 happy path 更有效。

## P-004 测试护栏打错层，被被测库自己绕过

**分类**：测试有效性 · **发现于** T-005 · **状态**：已修复

### 现象

为了保证"测试不真实触网"，加了 autouse 护栏 monkeypatch `httpx.AsyncClient.send`，
断言任何出网请求都失败。结果**所有 mock 用例全部误报护栏触发**。

### 根因

**打在了错误的抽象层。** 要让护栏拦得住"漏网的出网请求"，
拦截点必须**低于** respx 的 mock 接管点。httpx 的调用链是：

```
AsyncClient.send() → _transport_for_url() → Transport.handle_async_request() → httpcore → socket
     ↑ 第一次尝试          ↑ respx 接管点
```

- **第一次尝试**：patch `AsyncClient.send()` → 位于 respx 接管点**上层**，
  mock 请求和真请求**都**会被它拦下 → 所有 mock 用例误报失败；
- **第二次尝试**：patch `Transport.handle_async_request()` → 同样在 respx 接管点**上层**
  （respx 正是通过替换 `_transport_for_url` 返回 mock transport 实现的）→ 一样失效；
- **最终修复**：patch `socket.socket.connect` → 在链路**最底端**，
  是所有 HTTP 库（含 respx 注入的 mock transport）的必经之路。
  respx 生效时根本走不到 socket，护栏不触发；真漏网时立刻炸出 `AssertionError`。

**本质**：护栏的层次必须在被 mock 机制的**下方**才能测出"漏网"，
否则它测到的是"mock 有没有生效"——完全是另一件事。

### 修复

护栏改打到 **socket 层**：

```python
@pytest.fixture(autouse=True)
def _no_real_network(monkeypatch):
    def _blocked(self, *args, **kwargs):
        raise AssertionError("测试中禁止真实出网——请用 respx mock 回放厂商响应")
    monkeypatch.setattr(socket.socket, "connect", _blocked)
    monkeypatch.setattr(socket.socket, "connect_ex", _blocked)
```

### 如何防止重演

- 写"禁止某类操作"的测试护栏时，先确认**被测库的 mock 机制工作在调用链第几层**；
  护栏要放在它的**下方**，才能真正测到"有没有漏网"。
- 护栏本身必须有**反向验证**：故意写一个漏 mock 的用例，确认它会红。
  否则护栏可能只是个摆设——本条就是活证据：前两个版本看起来都"有护栏"，实际一个都没拦住。

## P-005 领域对象校验与契约校验重复，且触发点不一致

**分类**：契约先行 · **发现于** T-005 · **状态**：已修复

### 现象

领域层 `ChatRequest` 有 `if not messages: raise ValueError`，
API 层的 pydantic schema 却没写 `min_length=1`。
结果：空 `messages` 请求绕过了契约校验，直到领域层才抛 `ValueError`——
而 `ValueError` 不是 `DomainError`，最终变成 **500 而非 422**。

### 根因

**同一个约束写在了两层，但只有一层接入了错误处理链。**
领域层的校验是"最后一道防线"，API 层的校验才是"用户可理解的报错"。

### 修复

API 层 schema 补 `Field(min_length=1)`，让契约层就返回 422；
领域层的校验保留（防绕过 api 直接调服务的场景）。

### 如何防止重演

- 契约层（pydantic / OpenAPI schema）是**面向用户的错误**，领域层是**内部不变量**，
  两者都要有，**但要让用户触发的错误在契约层就被拦住**。
- 判断标准：如果一个输入错误返回了 5xx，就是漏了契约层校验。

## P-006 跨服务口头约定当契约用，导致身份头伪造可穿透

**分类**：安全 / 跨服务契约 · **发现于** T-005 ⇄ T-008 联合对齐 · **状态**：已修复

### 现象

Go 网关注入的用户身份头叫 `X-Subject-Id`，而 model-proxy 读的是 `X-User-Id`。结果：

- 网关注入的真实身份，model-proxy **读不到**；
- 客户端自己伪造的 `X-User-Id`，反而原样到达 model-proxy 并被当真。

**如果当时 `user_id` 已参与计量归属，这就是一个现成的跨租户串账漏洞。**
所幸 T-005 实现时 `user_id` 没有流入任何计费字段，所以没有实际发生。

### 根因

**"网关注入身份头"这件事从来没写进契约，只存在于两边的口头约定里。**
`packages/contracts/schemas/common.yaml` 里只有一个 `X-Tenant-Id`，
其余头名靠默契维持。两边各写各的，改了一边没人知道另一边对不上。

更深一层：这类缺陷**不会自己暴露**。T-005 单侧测试全绿（它读到的就是自己声明的头名），
T-008 单侧测试也全绿（它注入的就是自己声明的头名）——
**只有把两边放在一起看，才能发现名字不一样。**

### 修复

- 头名统一为 `X-User-Id`，两边对齐；
- T-008 改为转发前**剥离**全部身份头再注入（旧名一并剥离，防止客户端继续发旧名静默穿透）；
- `X-Trace-Id` 改为一律重新生成——trace_id 是对账关联键，沿用客户端值等于允许伪造对账依据；
- model-proxy 侧新增 `tests/unit/test_auth_trust_boundary.py`，锁定
  **`user_id` 不得进入 `InvocationContext` / `MeteringEvent`** 这条不变量：
  将来谁想把 user_id 接入计费，用例会失败并提示先解决可信来源。

### 如何防止重演

- **凡"跨服务传值"的东西，必须进契约**——头名也不例外。
  已与 T-008 共同上报 T-015，建议把网关注入头清单写进 `schemas/common.yaml`。
- **发现"缺失上下文"时按最坏情况评估**：不要因为"目前还没用上这个字段"就放过。
  这次是运气好，不是有设计。
- 加一条工程习惯：**两份独立的契约声明要对齐校验**。
  本项目已有先例——T-008 的 `TestRuleSetAlignmentWithModelProxy` 把两侧的 SSRF 网段表
  互相镜像成用例，任一侧改动都会在 CI 暴露。**这个手法值得推广到所有跨服务常量。**

## P-007 安全规则依赖标准库的隐式行为，跨版本可能静默失效

**分类**：安全 / 依赖隐式行为 · **发现于** T-005 ⇄ T-008 联合对齐 · **状态**：已修复

### 现象

T-008 提醒："IPv6 转换地址（6to4 / NAT64 / Teredo）是经典 SSRF 绕过手法，
你的网段表没有对应判定。"

我实测后发现一个**出乎意料的事实：当时并没有漏网**——
Python `ipaddress` 的 `is_private`/`is_reserved` 对这些段**已经判定为内网**，
所以在加显式规则之前它们就被拦住了。

但这恰恰是问题所在。

### 根因

**我的 SSRF 网段表里没有这些段，拦截完全依赖标准库的隐式行为。**

那些判定来自 IANA 特殊用途地址登记表，是 CPython 的**实现细节**，
不是我的代码里写下来的规则。三个风险：

1. **跨版本可能变**：判定依据是上游维护的登记数据，不是语言规范保证的不变量；
2. **静默失效**：真出问题时不会报错，只会放行——安全规则没有"报错"这个状态，
   这比会崩的 bug 更危险；
3. **不可审计**：评审者读我的网段表看不到这几段，无法判断"到底拦没拦"。

### 修复

1. **显式声明转换段**（`2002::/16` / `64:ff9b::/96` / `2001::/32` /
   `2001:2::/48` / `100::/64`），不再依赖标准库判定；
2. **抽内嵌 IPv4 复检**：6to4 / NAT64 / Teredo / IPv4-mapped 的内嵌 IPv4 会被提取出来，
   按 IPv4 规则再判一次。这样"构造一个段表没列到、但内嵌 127.0.0.1 的形态"也拦得住；
3. 测试同时锁住**行为契约**（这些地址必须被拦）与**表结构完整性**
   （转换段必须在自有表里显式出现）。

### 附带修掉：通配符白名单过宽

`*` 匹配原本写作 `lowered == candidate[2:] or lowered.endswith(candidate[1:])`，
其中 `== candidate[2:]` 让 `*.bigmodel.cn` 连裸域 `bigmodel.cn` 也匹配了。
已改为严格语义（只匹配子域，裸域需单独列出）——最小权限取向。

### 如何防止重演

- **安全规则要写在代码里，不能依赖库的默认行为。**
  判断标准：**如果删掉我的规则、靠库兜底也能工作，那这条规则就等于没写。**
- 库提供了"更严"的默认行为时，**仍要显式写出来**——理由不是当前有漏网，
  而是让规则可审计、且不随库版本漂移。
- 顺带一提：T-008 的 Go 侧确实有个**真实漏网**（`198.18.0.0/15` 误写成 `/19`，
  导致 `198.19.x.x` 放行），已修。**这说明两端各自维护网段表必然出错，
  正解是用测试互相镜像**（见 P-006 提到的手法）。

## 附：新增踩坑的格式要求

```markdown
## P-00X ⚠️ [资损/数据错误/架构盲区/反直觉]：一句话现象

**分类**：… · **发现于**：T-xxx · **状态**：已修复/待处理

### 现象
（用户/调用方看到的外部行为）
### 根因
（为什么代码看起来是对的——这才是有价值的部分）
### 修复
（具体改动）
### 如何防止重演
（可操作的规则/检查项，能落到测试或 CI 上）
```

**"根因"写得比"修复"更重要**：修复只解决这一次，
根因写清楚了才能让别人下次遇到同类问题直接绕开。
