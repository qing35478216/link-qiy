# 第一部分 总原则（先立规矩，再写代码）

## 1.1 审核人制度（一票否决，不可绕过）

**角色定义**：审核人 = Reviewer Agent（自动）+ 人类技术负责人（终审）。每个 PR 必须经审核人放行才能合并，**没有例外，包括 Orchestrator 自己的 PR**。

**三档裁决**：
- `ACCEPT`：可合并
- `REQUEST_CHANGES`：有问题必须改后重审
- `BLOCK`：触碰红线，一票否决，改哪儿都不许合并，必须人类介入

**十条一票否决红线**（触任一即 BLOCK）：
1. 改动超出工单文件领地（CI 自动检测）
2. domain 层 import 框架/ORM/HTTP 客户端
3. DB 查询无 tenant_id
4. 直接调模型厂商 SDK（必须走 model-proxy 客户端）
5. 业务代码里出现积分扣减（只能发 MeteringEvent）
6. 新增品类不走注册表、改引擎内核
7. 手写契约类型/SDK（api/ 和 types/ 必须生成）
8. 外部 URL 请求不过 ssrf-proxy；用户代码不进 sandbox
9. 资金相关无幂等设计
10. 单文件 >400 行或函数 >50 行且无豁免理由

**审核 SOP（30 分钟/PR）**：① 看 diff 领地（2 分钟）② 看红线十条（5 分钟）③ 看测试证据与开源选型记录（10 分钟：通用模块无调研记录=REQUEST_CHANGES）④ 看命名与结构（5 分钟）⑤ 抽一个核心函数读逻辑（8 分钟）。

**打回模板**：`[BLOCKING] 文件 x 行 y：违反红线 N（描述）→ 改法建议：…`；不许只写"有问题"不写改法。

## 1.2 防屎山军规（CI 强制，AI 无权跳过）

| # | 军规 | 执行方式 |
|---|---|---|
| 1 | **依赖方向**：api → services → domain → infra，禁止反向/跨层 | import-linter（Python）/ eslint boundaries（TS）CI 检查 |
| 2 | **文件体积**：单文件 ≤400 行，单函数 ≤50 行，圈复杂度 ≤10 | ruff C901 + wc 脚本 CI 门禁 |
| 3 | **重复率**：代码重复 ≤3% | jscpd / CPD CI 门禁 |
| 4 | **禁止模式**：any、as any、@ts-ignore、console.log、裸 SQL 字符串、硬编码密钥/IP、TODO 不带工单号 | lint 规则清单 |
| 5 | **抽象滞后**：同一模式出现 3 次才允许抽象；禁止为假想需求写抽象层 | Reviewer 人工判断 |
| 6 | **生成优于手写**：DTO/API 客户端/CRUD 路由/表格页面骨架一律生成 | 生成脚本 + diff 检查 |
| 7 | **命名即文档**：禁止 a/tmp/data/info 类命名；布尔必须 is/has 前缀 | lint + Reviewer |
| 8 | **删除义务**：重构 PR 必须列出删除清单；只增不减的 PR 需说明 | PR 模板字段 |
| 9 | **开源优先 + 依赖准入**：通用功能模块动手前必须先检索 GitHub 成熟开源库，选型核查四项（维护活跃度/Issue 响应/许可证兼容/技术栈匹配）；有多个候选必须列对比表给出推荐方案与理由；仅当现有库无法满足需求、体积过大或存在安全风险时才自研（工单写明理由）。新依赖进工单"依赖清单"（库名/版本/license/理由）+ 审核人批准，版本 pin | PR 检查 package 变更 + 开源选型记录必填 |
| 10 | **测试义务**：领域层覆盖率 ≥70%，新功能无测试 PR 直接打回 | CI 覆盖率门禁 |

## 1.3 精简开发三原则

1. **纵切优先**：每个功能先打通"UI → API → DB → 返回"最窄闭环，再补边角——禁止一层层平行铺（那是屎山的温床）
2. **配置优于代码**：能做成配置的（权益矩阵、检索参数、场景列表）不准写进代码
3. **MVP 只做 ★**：工单出现 ☆/○ 范围一律退回 Orchestrator
4. **不重复造轮子**：通用能力（文档解析/检索/存储/认证/限流/图表/流式…）先用成熟开源库，自研是最后选项——每造一个轮子，就是未来一份永远的维护债务

### 审核人检查点
- [ ] 适配器是否实现统一接口（无厂商 if-else 散落）
- [ ] 降级链是否可配置（禁止硬编码降级顺序）
- [ ] API Key 加密存储 + 脱敏返回（日志禁打印 key）
- [ ] 计量埋点是否在适配器出口统一发（禁止调用方各自发）
- [ ] 新厂商接入 diff 是否只新增文件（注册表模式验证）

# 第四部分 审核人工作手册

## 4.1 每个 PR 的审查动线（30 分钟）

```
① diff 领地（2min）  → git diff --name-only 对工单领地，超界=BLOCK
② 红线十条（5min）    → 逐条过 1.1 节清单
③ 测试证据+开源选型（10min） → CI 报告：lint/单测覆盖率/契约/黄金集，缺一=REQUEST_CHANGES；通用模块无开源调研记录=REQUEST_CHANGES
④ 结构命名（5min）    → 四层依赖/命名规范/禁止模式
⑤ 抽读核心逻辑（8min）→ 挑最复杂的 1 个函数顺逻辑，顺不动=REQUEST_CHANGES
```

## 4.2 分模块审查清单（速查）

| 模块 | 必查项（前 5） |
|---|---|
| 应用工厂 | 原子保存；code 不可变；跨租户 404；删除级联；脏标记全覆盖 |
| 模型框架 | 适配器接口统一；降级可配；Key 加密；计量统一出口；新厂商只加文件 |
| 提示词 | 模板版本化；优化计费；用户提示词只存不执行 |
| 知识框架 | 注册表模式；全异步可取消；双写一致性；抓取过代理；条数上限服务端校验 |
| 工具框架 | 路由有兜底；执行链可回放；schema 校验；工具无状态 |
| 嵌入 SDK | 双限流；渲染全转义；零依赖；白名单服务端强制 |
| 变现 | 整数金额；幂等；验签；对账告警；人类抽检 |
| 分发 | 深拷贝；物化；下架级联；种子数据化 |

## 4.3 打回与升级

- `REQUEST_CHANGES`：必须附改法建议；agent 修改后重审（只审改动点）
- 同一 PR 被打回 2 次 → 升级人类（防止 AI 死循环修）
- 黄金集分数连续 2 次下降 → 直接升级人类
- 每周输出《屎山风险报告》：超长文件 top10 / 重复率趋势 /  TODO 堆积
