## 交付说明

### 改了什么

在 `services/gateway/` 从零建 Go 网关骨架，33 个文件、8 次提交。四件事各自独立成包、**互不 import**：

| 机制 | 包 | 职责 | 依赖的内部包 |
|---|---|---|---|
| 鉴权 | `internal/auth` | JWT / API Key 校验，确立 Principal | 仅 `domain` |
| 限流 | `internal/ratelimit` | 租户 / 凭证 / 端点三维限流 | 仅 `domain` |
| 路由 | `internal/routing` | 上游与路由注册表、反代 | 仅 `domain` |
| CORS | `internal/cors` | console/service/embed 三组独立策略 | 仅 `domain` |

**三角分离的机器可验证证据**：上表「依赖的内部包」列全部只有 `domain`，
`domain` 自身不依赖任何内部包。包间通过 `domain` 的 context 键约定传数据
（`Principal` / `Surface`）——Go 的 context key 按类型比较，因此这两个键
必须定义在最内层，否则 auth 写入、ratelimit 读取永远命中不了。

**处理链顺序**：`路由解析 → CORS → 鉴权 → 限流 → 路由转发`。
路由拆成「解析」与「转发」两段，因为入口面必须在鉴权前可确定（CORS 的前提），
而转发必须看到 Principal（鉴权的产物）——一段做不到两件事。

其余：`internal/infra/` 四个适配器（jwt / apikey / tokenbucket / proxy）、
`internal/ssrf` 出站防护、`internal/config` 环境变量装配、`cmd/gateway` 进程入口、
`.golangci.yml`、README、选型对比表。

### 测试过程中发现并修复的真实缺陷

四个 bug 都是**自测发现的**，不是评审挑出来的，值得记录：

1. **限流超发（严重）**：`go test -race` 的并发用例实测「预算 50 的键放行了 200 个请求」。
   两处根因：① 每次请求都调 `rate.Limiter.SetLimit/SetBurst`，这两个方法会把令牌补满，
   等于每次请求都重置桶；② `ReserveN` 是「预约」语义，对未来时刻**恒返回 ok=true**，
   必须自行判定 `DelayFrom > 0` 并 `CancelAt` 才有拒绝语义。
   若无并发用例，这个网关会**静默地完全不限流**。

2. **SSRF 对 IPv6 直接 panic**：`IsPublicAddr` 无条件调 `net.As4()`，
   而 `As4()` 对 IPv6 会 panic。任何 IPv6 目标（`[::1]`、6to4、NAT64）
   都会让进程崩溃——本该被拒绝的请求变成拒绝服务。改为先判 `Is4()` 再取 `As4()`。

3. **CORS 装配顺序错误（跨域完全不可用）**：集成测试暴露预检返回 401/404 而非 204。
   装配链写成了「鉴权→限流→CORS→路由」，与设计注释相反。
   OPTIONS 预检不携带凭证，先过鉴权必然 401——**所有跨域调用都会失败**。
   附带修复：预检的实际方法在 `Access-Control-Request-Method` 头里，
   按 OPTIONS 方法匹配必然落空，新增 `LookupAnyMethod` 供预检使用。

4. **SSRF 端口解析可溢出**：`net.LookupPort` 接受服务名（"http"、"redis"）
   且返回 `int` 转 `uint16` 可能溢出。改为 `strconv.ParseUint` 严格解析 1-65535。

### 风险点

1. **限流是单进程内的（Phase 0 可接受，多实例部署前必须换）**
   `tokenbucket` 的配额存在进程内存里，多副本部署时每个副本各算各的，
   实际配额会放大 N 倍。接口已抽象好（`ratelimit.Limiter`），
   换 Redis 实现不动内核。**这是上线前必须处理的项**。

2. **API Key 存储用内存实现**（`apikey.MemoryStore`）
   骨架阶段够用，生产需接 Redis/DB。同样是接口已就绪（`apikey.Store`）。
   注意内存里存的是 Key 的 SHA-256 而非明文，这是刻意的安全设计。

3. **JWT 签名密钥通过环境变量注入**（符合铁律 5）
   未接 KMS，且未做密钥轮换机制。多实例部署时密钥必须一致，
   轮换需支持双密钥并存期。

4. **CORS 默认值偏宽松的部分**：`service` 组默认来源为空列表（= 完全不允许跨域），
   `embed` 组强制 `*` + 禁止凭证。前者需部署时配置，后者符合嵌入场景预期但需知悉。
   生产环境应显式配置 `GATEWAY_CORS_SERVICE_ORIGINS`，否则浏览器直连开放 API 会被拦。
   这属于**部署配置项，不是代码缺陷**，但运维需知悉。

5. **未做契约一致性验证**（Pact）
   网关是按 `packages/contracts` v0.1.1 的形状实现的（路由前缀、错误码、
   限流响应头），但本单**未与 T-010 的契约测试框架对齐**，
   也未跑契约测试。T-010 交付后需补一轮契约测试。
   已知的潜在不一致点：限流响应头（`X-RateLimit-Remaining`/`Retry-After`）
   与错误体（`{"error":"..."}`）的具体形状，是否与契约 v0.1.1 一致需核对。

6. **`golang.org/x/time` 版本降级**
   v0.16.0 要求 Go ≥1.26，本机 1.24.7 不满足，降级至 v0.12.0。
   若后续升级 Go 工具链，可回到 v0.16.0。已在选型文档记录。

### 关于「令牌桶为何不直接用标准库」的 ADR

需澄清一个事实：**我们用的就是 `golang.org/x/time/rate`，没有自己实现令牌桶算法**。
`internal/infra/tokenbucket` 的 `entry.limiter` 是 `*rate.Limiter`，
算法内核（令牌补充速率、突发容量计算）完全由官方库负责。

自研的是它外面的**一层键空间管理**，这层必须自研，原因是
`rate.Limiter` 表达不了我们的需求：

1. **多维度独立计数**：`rate.Limiter` 是单桶原语。我们的需求是
   租户 / 凭证 / 端点**三个维度各自独立计数、独立触发**，
   任一维度超额即整体拒绝，且响应头要反映"最受限"的那个维度。
   这套维度组合逻辑与"取最紧结果"的聚合规则，库里没有。
2. **键空间生命周期管理**：`rate.Limiter` 不管空闲键回收。
   多租户平台的租户数无上限，若不回收，`map` 会无限增长——这是
   真实的内存泄漏路径。`sweepLocked` + `entryTTL` 是我们必须自己做的。
3. **决策语义转换**：库返回 `Reservation`，我们要的是
   `{Allowed, Limit, Remaining, RetryAfter, ResetAt}` 的领域 `Decision`，
   并映射到 HTTP 状态码与 `X-RateLimit-*` 响应头。
4. **可替换性**：接口 `ratelimit.Limiter` 是我们的，官方库是其中一个实现。
   多实例部署时要换 Redis，届时只换实现不动中间件与聚合逻辑（铁律 4）。

**结论**：算法内核用官方库（不重复造轮子，铁律 8），
领域适配层自研（通用库无法满足的部分）。详见 `docs/踩坑记录.md` 第一节。

## 关于 `X-Forwarded-For` 的自查（gatekeeper 提问点）

gatekeeper 被要求重点复核"剥离全部身份头再注入"是否覆盖完整，
特别点名 `X-Forwarded-For`。我实测了，**结论是当前无漏洞**：

```
客户端伪造 X-Forwarded-For: 6.6.6.6, 7.7.7.7
→ 上游实际收到 X-Forwarded-For = 192.0.2.1（真实客户端 IP）
```

原因：`proxy.go` 的 `Rewrite` 钩子调用了 `httputil.ProxyRequest.SetXForwarded()`，
该方法是**覆盖语义**（不是 `httputil` 里 `ReverseProxy` 的追加行为），
会用真实连接信息重写该头，客户端伪造值不存活。

注意 `X-Forwarded-For` **不纳入** `identityHeaders` 剥离清单是正确的：
它是标准代理头，语义上应由反代层按真实连接信息生成，
而非像身份头那样由路由层注入。剥离它反而会让 `SetXForwarded` 失去作用。

### 限流超发的根因说明（主理人要求补）

主理人问「为什么这不只是少个 mutex」。**准确说：这不是锁的问题。**

锁是**正确的**——`tokenbucket.Limiter` 从一开始就有 `sync.Mutex`，
临界区覆盖了 map 读写（`mu.Lock()` 到 `defer mu.Unlock()` 包住整个取桶/建桶流程）。
`-race` 全程无告警。

真正的根因是**两个 API 语义误解**，与并发无关：

1. **`SetLimit`/`SetBurst` 会把令牌补满**。
   `SetBurstAt` 内部调 `advance(t)`，其返回值按新 burst 截断，
   等于把桶加满。最初每次请求都调用它们来"对齐配置"，
   于是每次请求都重置桶 → 限流完全失效（预算 50 放行 200）。

2. **`ReserveN` 不是拒绝语义**。它把请求**预约到未来**：
   连续调用时恒返回 `ok=true`，`delay` 递增。真正的拒绝语义是 `AllowN`。
   最初误把 `!OK()` 当作"超限"，于是没有任何请求被拒。

两者都与并发无关——**串行执行同样会超发**。
之所以是 `-race` 场景暴露，是因为该 bug 恰好在
`TestAllow_ConcurrentNeverExceedsLimit`（用原子计数断言实际发放数）
里被量化出来；只断言"不报错/不 panic"的串行用例抓不到。

这一点值得记进踩坑文档，因为下一个人写 Go 限流大概率会踩同样的 API 陷阱。
已写入 `services/gateway/docs/踩坑记录.md` 第一节，含 `rate.go` 源码引用与实测输出。

### 阻断项 1：令牌桶在并发下超发放行（限流失效）

**位置**：`services/gateway/internal/infra/tokenbucket/tokenbucket.go:110`

```go
now := l.now()        // ← 第 110 行：在 mu.Lock() 之前采样时钟

l.mu.Lock()            // ← 第 112 行
defer l.mu.Unlock()
```

**机制**（已用对照实验证明，非推测）：

1. goroutine A 在 T0 采样到 `now`，随即阻塞在 `mu` 上。
2. 其它 goroutine 用 T1（T1 > T0）推进桶，`lim.last = T1`。
3. A 拿到锁，把**过期**的 T0 传入 `e.limiter.ReserveN(now, 1)`。
4. `x/time/rate` 的 `reserveN` 在 ok 时执行 `lim.last = t`（rate.go 源码已核）
   → **`lim.last` 被拨回 T0**。
5. 后续请求 `advance(now)` 计算 `elapsed = now - lim.last` 时，
   把这段"已被消费过"的时间**再次计入补充量** → 凭空多出令牌。
6. `CancelAt` 会归还预留令牌，但**不会**把 `lim.last` 拨回去——
   故每被拒绝一次就漏掉一次时间窗口。

**实测证据**（配额 50/秒，128 goroutine × 500 次，理论上限 ≈ 51.7）：

```
原实现（now 锁外采样）：平均放行 141 → 超额 173%
修正版（now 锁内采样）：平均放行 51  → 超额  -1%
```

对照组只改一行（把 `now := l.now()` 移进锁内），超额从 173% 降到 -1%。
**因果链成立**——排除了"只是测试口径问题"的可能。

**缺陷形态**（重要，决定修复与验收方式）：超额量 ∝ **配置的补充速率**，不是固定值。

| 配额 | 补充速率 | 并发放行 | 理论上限 | 超额 |
|---|---|---|---|---|
| 50/小时 | 0.014/s | 50 | 50.0 | 0% |
| 50/分钟 | 0.83/s | 51 | 50.0 | +2% |
| **50/秒** | **50/s** | **174** | **51.3** | **+239%** |
| 1000/分钟（生产默认） | 16.7/s | 1040 | 1000.6 | +4% |

生产默认配额下突发（1000）掩盖了问题，但**稳态速率**仍被放大：
把突发吃干净后单独测量，**配置 16.67/s 实测 28.20/s，超 69%**。
即：配额越大、速率越高的租户被放大得越狠，而那正是付费高配额客户。

**为什么实现者的并发用例测不出来**：`tokenbucket_test.go` 的
`TestAllow_ConcurrentNeverExceedsLimit` 使用 `New(WithClock(func() time.Time { return fixedNow }))`
—— **冻结时钟**下所有 goroutine 读到同一个 `now`，过期时间戳窗口根本不会打开，
`lim.last` 无从被拨回。该用例在结构上无法暴露此缺陷。这不是疏忽，
而是测试方法与缺陷形态不匹配：用例断言的是"冻结时钟下的正确性"，
而真实风险发生在"时钟前进 + 锁竞争"下。

**必须修复**：`tokenbucket.go:110` 的 `now := l.now()` 移入 `mu.Lock()` 之后，
并补一条**使用真实时钟（不注入 frozen clock）**的并发回归用例，
断言"放行数 ≤ burst + 补充速率 × 耗时"。

```
      .../internal/infra/apikey/apikey.go:120
```

`MemoryStore.keys` 是裸 `map`，`Add`/`Lookup` 均无锁，而 `Lookup` 在
请求路径上被 `Authenticator.Authenticate` 调用（apikey.go:73）。

**当前可达性**：低。`Add` 在生产代码中无调用点（已 grep 全量确认），
即默认路径下 map 只读不写，Go 的并发只读 map 是安全的。
**但**：`server.buildAuth` 在 `KeyStore == nil` 时回落到 `NewMemoryStore()`（server.go:141-143）。
一旦后续任何管理接口（创建/轮换 Key）在运行时调 `Add`，
就是真实的可利用竞态，且 Map 并发写会直接 `fatal error: concurrent map writes` 崩进程（DoS）。

**定级**：重要级，非本次阻断（因当前不可达），但**必须在接入任何 Key 管理接口之前修复**。
修法：`MemoryStore` 加 `sync.RWMutex`，或改为 `sync.Map`。

### 重要级：SSRF 闸门是死代码，未接入任何生产路径

`internal/ssrf` 的实现质量很高（见下"实测通过项"），但：

```
$ grep -rn "internal/ssrf" --include="*.go" . | grep -v _test.go
./internal/infra/proxy/proxy.go:5:// 因此不需要（也不提供）SSRF 防护——出站到用户 URL 的场景请走 internal/ssrf。
```

**除注释外，零引用**。`Guard.Validate / Transport / Client / DialContext`
在生产路径中无任何调用点；`proxy.ReverseProxy` 用的是裸 `net.Dialer`。

**风险**：当前网关只向**配置内注册的上游**转发（目标来自环境变量，非用户输入），
所以现在**没有可利用的 SSRF 入口**。但闸门"默认放行"——任何后续引入
用户可控 URL 的功能（webhook 回调、链接预览、从 URL 导入），
若忘记接 `ssrf.Guard`，就是直接的 SSRF 漏洞，而工具箱就在旁边。

**要求**：
1. 在 `proxy` 的 Transport 上接入 `ssrf.Guard`（配置内上游可经 `WithAllowedHosts` 显式豁免），
   或在架构守卫测试中加断言：**`internal/ssrf` 被零引用时 CI 失败**，
   强制"要么在用，要么删掉"，杜绝死代码式安全。
2. 上游 Target 增加启动期校验（当前 `config.Validate()` 只检查非空，不校验是否合法 http(s) URL）。

### 阻断项 1：限流并发超发（+227.9% → -0.3%）

**根因**：`tokenbucket.go` 的 `now := l.now()` 采样在 `mu.Lock()` **之外**。

机制：高并发下 N 个 goroutine 全部在锁外读到同一个旧时间戳，进锁后
`ReserveN(now, 1)` 判定"无需等待"。而 `x/time/rate` 的 `reserveN` 在 ok 时
执行 `lim.last = t`——**过期时间戳把 `lim.last` 拨回过去**；后续 `advance()`
便把"已被消费过的那段时间"重复计入补充量，凭空多令牌。
`CancelAt` 归还令牌但不回拨 `lim.last`，故每被拒一次就漏一次时间窗口。

**这是我的修复引入的**：上一轮我把 `SetLimit/SetBurst` 移到正确位置，
却漏了紧邻的时钟采样。

**实测**（配额 50/秒，128 goroutine × 500 次）：

| | 放行数 | 理论上界 | 超额 |
|---|---|---|---|
| 修复前 | **170** | 51.8 | **+227.9%** |
| 修复后 | 51 | 51.1 | -0.3%（`-count=5` 稳定） |

**修复**：`now` 移入临界区。一行改动。

**为什么原有用例测不出**：`TestAllow_ConcurrentNeverExceedsLimit` 注入
**冻结时钟**（`WithClock(func() time.Time { return fixedNow })`），
时间不推进，所有 goroutine 读到同一个 `now`，缺陷形态根本无法出现。
这是**测试方法与缺陷形态不匹配**，不是运气问题——
结构性问题，光加一条同形态用例没用。

新增 `internal/infra/tokenbucket/gateproof_test.go`：**真实推进时钟**，
断言"放行数 ≤ burst + 补充速率 × 耗时"（留 25% 抖动余量）。

#### DNS rebinding（实现者最没底处 —— 实测通过）

构造真实 rebinding：第 1 次解析给公网 IP 骗过校验，之后翻转 `127.0.0.1`。

故调用方连接时不会重新解析，TOCTOU 窗口被真正消除（不是"逻辑上成立"，是实测成立）。

2. 剥离 + 重注入已经达到安全目标（下游拿到的值100% 来自网关），且可审计。

## 补充：头剥离的完整分级（@ 6899e88）

主理人指出我的机制描述有偏差，并要求如实分级。核实后确认描述确实有误。

### 机制更正：不是"漏剥离"，是"语义不同类"

我原话说"这 5 个 IP 头不在 `identityHeaders` 里，所以被透传"。
准确说法是：**它们本来就不是身份头**。

- `identityHeaders` 定义域 = "**网关注入的调用方身份**"（X-Tenant-Id / X-User-Id /
  X-Gateway-Surface / X-Trace-Id / traceparent）
- IP 类头（X-Real-IP 等）语义上属于"**转发链信息**"
- `SetXForwarded()` 只覆盖 XFF 本身，其余是**默认透传**的结果，不是漏剥离

**这个区别必须写准**：否则下一个人会去 `identityHeaders` 里加 IP 头，
那才是错的——会把"网关管辖的身份"与"转发链信息"混成一个清单。

已按建议分成两组，各归其位：

| 组 | 位置 | 语义 | 处理方式 |
|---|---|---|---|
| `identityHeaders` | `internal/routing` | 网关注入的调用方身份 | 剥离后注入可信值 |
| `clientCredentialHeaders` | `internal/routing` | 客户端凭证载体 | 剥离（网关是唯一鉴权决策点） |
| `clientIPHeaders` | `internal/infra/proxy` | 转发链信息 | 剥离后由 `SetXForwarded()` 重写 |

### Authorization / Cookie 透传（qa-reviewer 指出）

实测确认：`Authorization: Bearer <client-jwt>` 与 `Cookie: session=...`
原样到达下游。

风险：网关已完成鉴权与配额裁决，下游若自行校验，看到的是**客户端原始凭证**
而非网关的裁决结论——可能"网关已封禁/限流，下游却按自己的判断放行"，
形成**双重鉴权入口**。

修复：新增 `clientCredentialHeaders`（含 `Proxy-Authorization`）一并剥离。
新增 `TestStripsClientCredentialHeaders`，并断言
"剥离凭证头不影响网关注入的身份头"。

### legacyIdentityHeaders 的来历（主理人要求查清）

来历：T-005 对齐时本网关用 `X-Subject-Id`，下游 model-proxy 读 `X-User-Id`，
命名不一致 → 真实身份断流 + 客户端伪造值畅通。统一为 `X-User-Id` 后成为废弃名。

**为什么仍要剥离**：灰度期客户端可能仍在发旧名（缓存的 SDK、第三方集成），
不剥离会静默穿透，造成"看起来有身份、来源不明"的排查噩梦。
**废弃 ≠ 不管**——这是安全头与普通 API 的差别。
已加 `TestLegacyIdentityHeaderStillStripped` 锁定，
防止后人"清理无用代码"时顺手删掉。

### 如实分级（本轮无被利用漏洞）

**本轮修的三项，当前均无可利用路径**，已逐项核实下游消费情况：

### 评审方法学记录（本轮两处自我纠正）

1. **首版 rebinding 用例假通过**：默认端口白名单只放 80/443，测试用随机端口会在
   DNS 解析**之前**被端口校验拦下（`DNS 查询次数=1` 即为征兆）。
   显式 `WithAllowedPorts(测试端口)` 后查询次数升到 7，才真正走到 rebinding 路径。
   **若当时没看"查询次数"这个指标，我会误判为"rebinding 防线成立"**——
   而它其实根本没被测到。
2. **两处期望写错被误判为缺陷**：`198.20.0.1`（`/15` 之外，放行正确）、
   `0177.0.0.1`（本机 resolver 按十进制解析为真实公网 `177.0.0.1`，放行正确）。
   第二处反而揭示了设计的优点：**闸门校验解析后的 IP 而非字符串形态**，
   故各平台对八进制/短格式的解析差异天然被覆盖。
