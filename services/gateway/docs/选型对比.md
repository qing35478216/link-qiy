## 一、网关框架：为什么自研而非引入成熟网关

### 候选对比

| 方案 | 语言 | License | 最后推送 | 语言/架构契合度 | 结论 |
|---|---|---|---|---|---|
| Kong OSS | Lua / OpenResty | Apache-2.0 | 持续活跃 | 需 PostgreSQL 或声明式配置中心，插件写 Lua；我们是 Go 单二进制 + 环境变量配置 | ✗ 引入 Lua 运行时，团队无 Lua 技术栈 |
| Apache APISIX | Lua / OpenResty | Apache-2.0 | 持续活跃 | 强项是多语言插件与 etcd 动态配置，我们是 Phase 0 单服务静态配置 | ✗ 同上，且 etcd 是额外部署组件 |
| Traefik | Go | MIT | 2026-10-12 | **同为 Go**；零配置 + 自动服务发现 | △ 技术栈匹配，但其核心价值是「容器编排自动发现」，我们路由表来自平台自身配置 |
| Envoy Gateway | C++ / Envoy | Apache-2.0 | 持续活跃 | xDS 动态配置，面向服务网格 | ✗ C++ 侧需额外部署，且我们不需要 mesh |
| **自研（net/http + chi）** | Go | — | — | 与全站技术栈一致；无额外部署组件 | **✓ 采纳** |

### 采纳理由

docs/03 第 3.2 节技术选型表已明确结论「网关：Go（自研轻量）」，本文补充铁律 8 要求的核查：

1. **职责不重叠**：Kong / APISIX / Traefik 的核心能力是「插件市场 + 配置中心 + 服务发现」。
   本单要求的鉴权 / 限流 / CORS 三角分离，需要的是**能精确控制每组策略注册时机与隔离边界**的能力，
   通用网关的全局插件模型反而会破坏这个隔离性（无法保证 console 组策略不污染 service 组）。
2. **多租户是硬需求**：铁律 6 要求所有操作带 tenant_id。通用网关的多租户模型
   （通常基于 consumer / apikey）与我们「租户 → 配额 → 凭证」的三级模型不匹配，
   强行套用需要在网关侧再写一遍适配层，反而更复杂。
3. **渠道网关的长连接诉求**：docs/03 要求渠道走 WebSocket / 长轮询、压测 10k 长连接。
   这需要在同一进程内精细控制连接生命周期与背压，通用网关的抽象不提供这个控制点。
4. **安全基线内建**：ssrf-proxy 是铁律 5 的硬性要求，必须与出站请求在同一进程内
   强制生效（而非依赖「配置对了就生效」），自研才能保证这一点。

**代价与风险**：我们放弃了成熟网关的插件生态与可视化控制台。
缓解：横切机制全部走「接口 + 注册表」，后续要接 Redis 限流、mTLS、
OAuth2 等能力时按适配器扩展，不改内核（见下文各模块的扩展点说明）。

## 二、路由：go-chi/chi

| 候选 | License | 最后推送 | Star | open issues | 结论 |
|---|---|---|---|---|---|
| **github.com/go-chi/chi/v5** | MIT | 2026-10-12 | 22.9k | 126 | **✓ 采纳** |

四项核查：
- **① 活跃度**：最后推送 2026-10-12，距采集日 1 天，✓
- **② Issue 响应**：126 open / 3.5k fork，规模健康，维护活跃，✓
- **③ 许可证**：MIT，可直接引入，✓
- **④ 技术栈匹配**：v5.4.0 要求 Go ≥1.23，本机 1.24.7 可用，✓

选它的理由：本单只需要「路径前缀匹配 + 中间件链 + 按分组装配」。
chi 的 `Group` / `Use` 组合语义正好对应我们「四段横切机制 + 多入口面」的装配需求，
且无第三方依赖（仅 stdlib）。

> 注：路由匹配的核心逻辑（最长前缀优先）由我们自己实现在 `routing.Table.Lookup`，
> chi 只负责 HTTP 方法/路径的分发。之所以不直接用 chi 的路由匹配，是因为我们需要
> 「同一路径前缀按方法注册多条路由 + 入口面标记」这类自定义语义。

  兼容字符串与字符串数组两种 scope 编码。

## 四、CORS：自研（未引入 rs/cors）

| 候选 | License | 最后推送 | Star | open issues | 结论 |
|---|---|---|---|---|---|
| github.com/rs/cors | MIT | 2026-10-08 | 2.9k | 28 | △ 见下 |
| **自研 internal/cors** | — | — | — | — | **✓ 采纳** |

四项核查（rs/cors）：① 2026-10-08 活跃 ✓ ② 28 open / 2.9k star 健康 ✓
③ MIT ✓ ④ 无依赖 ✓。**它是一个合格的库，技术上完全可用。**

不采纳的理由是需求不匹配，而非质量不足：

1. **铁律要求的三组策略隔离，rs/cors 的抽象不支持**。它是「一个 `Cors` 实例包一个 handler」，
   要实现 console/service/embed 三组互不串染，需要在路由层维护三个实例并保证请求只进入其一——
   隔离逻辑会散落在装配代码里，而不是收在 CORS 模块内。工单验收标准 3 要求
   「用例证明三组策略互不串染」，自研让这个断言落在单个包的注册表里，测试可直接覆盖。
2. **安全默认值需要前置校验**。规范禁止「`Access-Control-Allow-Origin: *` 与
   `Allow-Credentials: true` 同时出现」，rs/cors 不阻止这种配置（它由调用方保证）。
   本单把它做成 `NewPolicy` 的**构造期硬校验**，配错直接返回 error、启动失败，
   而不是运行时静默产生一个危险策略。
3. **无鉴权前置的预检短路**。我们的装配顺序要求 CORS 排在鉴权之前
   （预检不带凭证），rs/cors 的 handler 只能整体包裹，无法只替换其中一段。

**代价与风险**：需要自己维护 CORS 规范细节。缓解：核心行为（来源/方法/头匹配、
预检响应头、通配与凭证互斥）均有对应用例，且参考 RFC 6454 与 rs/cors 的实现语义。

> 曾在 go.mod 中引入 rs/cors，因最终未使用已移除（`go mod tidy` 清理）。

## 五、限流：golang.org/x/time/rate + 自研键空间

| 候选 | License | 最后推送 | 结论 |
|---|---|---|---|
| github.com/ulule/limiter/v3 | MIT | **2024-12-10** | ✗ 见下 |
| github.com/throttled/throttled | MIT | 活跃 | △ 需接 Redis |
| **golang.org/x/time/rate**（算法内核） | BSD-3-Clause | 2026-09-08 | **✓ 采纳** |

**ulule/limiter 不采纳的理由**（这是本次调研最实质的发现）：
最后推送 **2024-12-10**，距采集日 **2026-10-13 已 22 个月**，
不满足铁律 8 核查项 ①「近 3 个月有提交或发版」。
对一个处于安全链路上的限流组件，22 个月无维护是实质风险，不能因 MIT 方便就引入。

**为何仍需自研外层**：x/time/rate 只提供「单个令牌桶」原语，
而我们需要的是「按 租户 / 凭证 / 端点 三个维度独立计数并独立触发」——
键空间管理、维度组合、闲置键回收、`Retry-After` 语义都要自己实现。
这部分逻辑是我们真正的领域知识，用现成的"限流中间件"反而要逆向适配。

集成方式：`internal/infra/tokenbucket` 把 `rate.Limiter` 包成 `ratelimit.Limiter` 接口的实现，
生产换成 Redis 后端时接口不变（铁律 4：适配器 + 注册表）。

> **实测踩坑（已修复并有回归用例）**：`rate.Limiter.SetLimit` / `SetBurst`
> 会把令牌补满，若每次请求都调用，桶被无限续命、限流形同虚设。
> 并发用例实测：预算 50 的键实际放行 200 个请求。
> 另 `ReserveN` 是「预约」语义，对未来时刻恒返回 `ok=true`，
> 必须自行判定 `DelayFrom > 0` 并 `CancelAt` 才能得到拒绝语义。

版本约束：`x/time` v0.16.0 要求 Go ≥1.26，本机 1.24.7 不满足，**降级至 v0.12.0**（兼容 Go 1.18+）。

## 六、SSRF 防护：自研（候选均为新项目，风险不可接受）

| 候选 | License | 最后推送 | Star | 结论 |
|---|---|---|---|---|
| github.com/doyensec/safeurl | Apache-2.0 | 2026-06-11 | 116 | ✗ 见下 |
| github.com/cplieger/ssrf/v4 | Apache-2.0 | 2026-06 | 新项目 | ✗ 要求 Go ≥1.27.2，本机 1.24.7 不满足 |
| github.com/chrj/ssrf | MIT | 2026-10-09 | **0** | ✗ 2026-04 才创建，0 star |
| github.com/abhinavxd/ssrfguard | MIT | 2026-02-15 | **3** | ✗ 单次提交，3 star |
| **自研 internal/ssrf** | — | — | — | **✓ 采纳** |

**doyensec/safeurl 是最接近的候选**（Apache-2.0、安全领域知名），
不采纳的理由：它是一个**独立的 mTLS 出口代理服务**（需额外部署一个进程 + 客户端证书体系），
而 Phase 0 阶段我们要的是**库形态的出站守卫**，直接嵌在 `http.Transport` 上。
引入它等于为 Phase 0 多加一个部署组件。

**其余三个候选是更关键的问题**：chrj/ssrf（2026-04 建仓、0 star）与
ssrfguard（3 star、单次提交）都是近几个月出现的新项目，
没有任何 Issue 历史与社区验证。把**安全基线的最后一道防线**
押在未经审计的新项目上，风险高于自研——这符合铁律 8「存在安全风险时才允许自研」。

自研部分（`internal/ssrf`，仅依赖标准库）实现了三层防御，任一层单独都不够：
1. **URL 静态校验**：scheme 仅 http/https、拒绝 userinfo、端口限 1-65535 且需在白名单
2. **DNS 解析后校验**：解析出的**每一个** IP 都必须公网可路由（多 A 记录部分内网也拒绝）
3. **连接时校验**：`net.Dialer` 解析一次 → 校验 → **连字面 IP**，
   消灭 DNS rebinding 的 TOCTOU 时间窗；重定向每一跳重新校验

覆盖的绕过手法：IPv6 转换地址内嵌私网 IPv4（6to4 / Teredo / NAT64）、
`::ffff:` 映射地址、CGNAT 100.64/10、链路本地（云元数据 169.254.169.254）、
文档保留段、非 http(s) 协议、userinfo 注入、非常规端口（6379/9200/11211 等内网扫描）。

## 八、后续扩展点（铁律 4：适配器 + 注册表）

新增能力一律加适配器，不改内核：

| 需求 | 做法 | 是否改内核 |
|---|---|---|
| 新认证方式（OAuth2 / mTLS / 内部票据） | 实现 `auth.Authenticator` → `auth.Registry.Register` | 否 |
| 分布式限流（多实例） | 实现 `ratelimit.Limiter`（Redis 实现）→ 注册为策略后端 | 否 |
| 新渠道（微信 / 飞书 / 钉钉 / 嵌入） | 实现渠道适配器接口 → 渠道注册表；作为新 Upstream 接入路由 | 否 |
| 新 CORS 入口面 | `cors.NewPolicy` + `Registry.Register` | 否 |
| 新后端服务 | `Table.RegisterUpstream` + `Table.RegisterRoute` | 否 |
