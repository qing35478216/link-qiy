## 一、令牌桶超发：两个 API 语义陷阱

### 现象

并发压测实测：**预算 50 的键，实际放行 200 个请求**。
串行用例全过，只有 `-race` + 计数断言能发现。

### 根因 1：`SetLimit` / `SetBurst` 会把令牌补满

```go
// ❌ 错误写法：每次请求都"对齐配置"
e.limiter.SetLimitAt(now, perSecond)
e.limiter.SetBurstAt(now, burst)
```

读 `golang.org/x/time@v0.12.0/rate/rate.go` 的 `SetBurstAt`：

```go
func (lim *Limiter) SetBurstAt(t time.Time, newBurst int) {
	tokens := lim.advance(t)
	lim.last = t
	lim.tokens = tokens      // ← advance() 会按新 burst 上限截断
	lim.burst = newBurst
}
```

`advance()` 返回的令牌数被 `min(tokens, burst)` 截断，
所以每次调用 `SetBurst` 等于**把桶加满**。每次请求都调 = 桶被无限续命。

**修法**：只在配置真正变化时调用。

```go
if e.limit != perSecond {
	e.limiter.SetLimitAt(now, perSecond)
	e.limit = perSecond
}
if e.burst != burst {
	e.limiter.SetBurstAt(now, burst)
	e.burst = burst
}
```

**顺带一个隐蔽点**：这两个方法内部用 `time.Now()`，不是 `SetLimitAt`
传入的时间。若注入了测试时钟，桶会按真实时间推进，测试结果不可复现。
必须用 `SetLimitAt` / `SetBurstAt` 显式传时间。

### 根因 2：`ReserveN` 不是「拒绝」语义

```go
// ❌ 错误写法：以为 OK()==false 表示超限
reservation := lim.ReserveN(now, 1)
if !reservation.OK() { /* 拒绝 */ }
```

实测 `ReserveN(now, 1)` 在 burst=3、连续调用 6 次时**每次都返回 `ok=true`**：

```
i=0 ok=true delay=0s
i=1 ok=true delay=0s
i=2 ok=true delay=0s
i=3 ok=true delay=333.333333ms   ← 明显该拒了，却 ok=true
i=4 ok=true delay=666.666666ms
i=5 ok=true delay=1s
```

`reserveN` 的判定是 `ok := n <= lim.burst && waitDuration <= maxFutureReserve`——
它把请求**预约到未来**而不是拒绝。`Rate.Limiter` 里真正的"拒绝"语义是 `AllowN`。

**修法**：用 `ReserveN` 拿到等待时长，但自己判定是否可接受：

```go
reservation := e.limiter.ReserveN(now, 1)
if !reservation.OK() {
	// n 超过突发容量：等不到令牌，直接拒绝
	return 拒绝
}
delay := reservation.DelayFrom(now)
if delay > 0 {
	reservation.CancelAt(now)   // 需要等未来 → 拒绝，并把预留的令牌还回去
	return 拒绝(RetryAfter: delay)
}
```

注意用 `CancelAt(now)` 而非 `Cancel()`——后者内部同样用 `time.Now()`。

### 复现命令

```bash
go test -race -count=3 -run 'TestAllow_Concurrent' -v ./internal/infra/tokenbucket/
```

`TestAllow_ConcurrentNeverExceedsLimit` 用原子计数断言"实际发放数 ≤ 上限"，
这是能抓住该 bug 的关键——只断言"不 panic"或"不报错"抓不到。

## 二、context key 必须定义在最内层

### 现象

鉴权包写入的 Principal，限流包永远读不到。

### 根因

Go 的 `context.WithValue` **按 key 的类型比较**，不是按值。
最初我在 `auth` 和 `ratelimit` 里各自定义了：

```go
type principalKey struct{}   // auth 包的
type principalKey struct{}   // ratelimit 包的 —— 看着一样，但是不同类型
```

两个未导出类型即使字面完全相同，也**互不相等**，读取永远 miss。

**修法**：把 key 类型定义在 `domain`（最内层），两边共用。

```go
// internal/domain/context.go
type principalKey struct{}
func WithPrincipal(ctx context.Context, p Principal) context.Context {
	return context.WithValue(ctx, principalKey{}, p)
}
func PrincipalFrom(ctx context.Context) (Principal, bool) {
	p, ok := ctx.Value(principalKey{}).(Principal)
	return p, ok
}
```

**附带收益**：`auth` 与 `ratelimit` 由此实现真正的零 import 依赖——
"三角分离"不是靠约定，是靠类型系统保证的。

**推广**：任何跨包传递的 context key 都该这样。别用字符串 key
（`context.WithValue(ctx, "tenant", ...)` 官方已不推荐，会有 vet 告警）。

## 三、`netip.Addr.As4()` 对 IPv6 会 panic

### 现象

`ssrf.IsPublicAddr()` 收到任何 IPv6 地址直接 panic，
连 `[::1]` 这种本该"拒绝"的请求都会让进程崩溃——**拒绝服务**。

### 根因

```go
// ❌ 错误写法
if v4 := a.As4(); isCGNAT(v4) { ... }
```

`As4()` 在 `Addr` 不是 4 字节表示时 panic，**不是返回错误**。
而 `IsPublicAddr` 会被 IPv6 分支（6to4 / Teredo / NAT64 检查）递归调用，
于是任何 IPv6 目标都会走到这里。

**修法**：先判地址族再取值。

```go
a = a.Unmap()          // ::ffff:127.0.0.1 → 127.0.0.1
if a.Is4() {
	v4 := a.As4()
	// ...IPv4 专属判断
}
```

### 为什么 `Unmap()` 不能省

IPv4-mapped IPv6（`::ffff:127.0.0.1`）是 SSRF 绕过 SSRF 的经典手法：
字面是 IPv6，但 `Is4()` 为 false、`Is4In6()` 为 true。
不 `Unmap()` 就走 IPv6 分支，IPv4 专属的网段表全部失效。

实测覆盖情况（`TestProbeEncodedVariants`）：

| 输入 | `netip.ParseAddr` | 结果 |
|---|---|---|
| `::ffff:127.0.0.1` | 成功 → Unmap 为 `127.0.0.1` | 阻断 ✓ |
| `::ffff:7f00:1` | 成功 → 同上 | 阻断 ✓ |
| `0:0:0:0:0:ffff:127.0.0.1` | 成功 → 同上 | 阻断 ✓ |
| `2130706433`（十进制） | **解析失败** | 阻断 ✓ |
| `0x7f000001`（十六进制） | **解析失败** | 阻断 ✓ |
| `0177.0.0.1`（八进制） | **解析失败**（前导零） | 阻断 ✓ |
| `127.1`（短格式） | **解析失败** | 阻断 ✓ |

后四种由 `net/netip` 本身拒绝——这是用标准库而非 `net.ParseIP` 的额外收益。
`net.ParseIP` 会接受十进制/短格式等非规范写法。

**教训**：涉及 IP 判定时优先用 `net/netip`（严格、无 panic、区分地址族），
而不是老的 `net` 包。

## 四、CORS 装配顺序：CORS 必须先于鉴权

### 现象

集成测试里 CORS 预检返回 401/404，所有跨域调用失败。

### 根因（两个叠加）

**其一，装配链写反了**。最初写成：

```go
api.Use(authMW.Handle)      // ✗ 预检在这里就 401 了
api.Use(limitMW.Handle)
api.Use(corsMW.Handle)     // 永远到不了
api.Use(routeMW.Handle)
```

OPTIONS 预检请求**按规范不携带凭证**，先过鉴权必然 401。
正确顺序：`路由解析 → CORS → 鉴权 → 限流 → 转发`。

**其二，路由"匹配"和"转发"不能合成一段**。矛盾在于：
- 入口面（决定用哪组 CORS 策略）必须在鉴权**前**可确定；
- 转发必须看到 Principal（鉴权的产物）才能注入租户头。

拆成两段解决：`Resolver` 只匹配+标记入口面，`Middleware` 校验租户+转发。

**其三（附带）**：预检的实际方法在 `Access-Control-Request-Method` 头里，
请求行方法恒为 `OPTIONS`。按方法匹配路由必然落空，
故新增 `LookupAnyMethod` 专供预检使用。

## 五、身份头：网关是唯一可信来源

### 现象

下游服务（model-proxy）信任网关注入的 `X-User-Id`，
但网关**只注入、不剥离**客户端传入的同名头。
实测：客户端携带 `X-User-Id: victim-user-9999` → 上游原样收到该伪造值。

更糟的是网关注入的是 `X-Subject-Id`，与下游读的 `X-User-Id`
**根本不是一个名字**——真实身份永远传不过去，伪造的那个反而畅通。

### 修法

```go
// 顺序不可反：先注入再剥离会把可信值也删掉
sanitizeIdentityHeaders(r)   // 剥离客户端伪造
r.Header.Set(HeaderTenantID, p.TenantID)  // 注入可信值
```

`X-Trace-Id` 由「有则沿用」改为一律重新生成：
trace_id 是计费对账与审计的关联键，沿用客户端值等于允许伪造对账依据。

**上线前的教训**：我写完 `sanitizeIdentityHeaders` 后，
回归用例 `TestNoSubjectIDHeaderLeaks` 当场抓到我自己漏加了旧名
`X-Subject-Id` 的剥离。**只要客户端还在发旧名，它就会静默穿透**——
所以废弃的头名也要留在剥离列表里。

## 六、跨语言常量对齐：用测试锁定，不靠口头约定

### 问题

Go 与 Python 各有一套 SSRF 网段表。两侧漂移会出现
"同一目标地址在 A 服务被拒、在 B 服务放行"的诡异 bug。

### 修法

把另一侧的规则表**逐条镜像成 Go 侧的测试用例**：

```go
// 镜像 model-proxy 的 _BLOCKED_NETWORKS / BLOCKED_HOSTS
{host: "198.18.0.1", why: "198.18.0.0/15 基准测试网"},
{host: "198.19.255.255", why: "198.18.0.0/15 上界"},
...
```

任一侧改网段表，Go 侧测试立即失败。

**它当场抓到了真 bug**：Go 侧把 `198.18.0.0/15` 误写成 `198.18/19`，
导致 `198.19.x.x` 从网关侧漏放。

比"共用一份常量文件"更强的点：它连**常量抄错**都能抓
（`/15` 写成 `/19` 是抄写错误，不是规则分歧）。

**方向性约定**：Go 侧作为第二道防线可以更严（多阻断），不得更松（少阻断）。
用 `TestGoSideIsStricterOrEqual` 锁住，防止后续"简化"时被误删。

## 七、`golangci-lint` v2 配置：写错不报错，静默失效

### 现象

`.golangci.yml` 里写了 `issues.exclude-rules`，跑起来没报错，
但测试文件的告警一条没少——排除规则**根本没生效**。

### 根因

v2 移了位置。正确写法是 `linters.exclusions`（与 `linters.settings` **平级**）：

```yaml
linters:
  settings:
    gosec: {...}
  exclusions:          # ← 与 settings 平级，不在 settings 里面
    rules:
      - path: _test\.go
        linters: [errcheck, gosec]
```

三个错误位置（都不报错）：
- `issues.exclude-rules`（v1 位置）
- `linters.settings.exclusions`（嵌在 settings 里）
- `linters.exclusions` 但缩进错

### 教训

**改完配置必须校验**，否则你以为配好了其实没生效：

```bash
golangci-lint config verify   # 位置写错会明确报 jsonschema 错误
```

这个坑的特点是"沉默地不工作"——不校验的话，会一直以为测试文件被豁免了。

## 八、小结：这些坑的共性

| 类别 | 案例 | 共性 |
|---|---|---|
| **API 语义误解** | `SetBurst` 补满令牌、`ReserveN` 非拒绝语义 | 名字符合直觉 ≠ 行为符合直觉 |
| **语言规则细节** | context key 按类型比较 | 看着一样的代码，语义不同 |
| **标准库陷阱** | `As4()` panic 而非返回 error | 危险 API 需确认失败模式 |
| **装配顺序** | CORS 须先于鉴权 | 顺序本身承载安全语义 |
| **安全默认值** | 身份头只注入不剥离 | "信任边界"要显式建模 |
| **配置漂移** | 跨语言网段表、`golangci-lint` 静默失效 | 靠约定必然漂移，靠机器锁定 |

**贯穿性教训**：以上 8 条里，**有 6 条是测试发现的**，
且多数是"只断言不报错/不 panic"抓不到、必须断言**具体值**才能暴露
（发放数、收到的头、上游收到的内容）。写断言时要问：
"这个测试失败的话，会告诉我哪个值不对？"
